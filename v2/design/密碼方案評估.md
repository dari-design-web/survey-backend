# G7｜Apps Script 後台密碼方案評估

日期：2026-11-02。狀態：**建議交付，尚未選定、實作或遷移**。依固定提交 `0804112cf6ef656958ca9d1b29992a902328322e` 的後端 3.2.0 評估，只處理後台人員登入；客人填問卷仍免登入。

## 建議

若後台人員都有可使用的個人 Google 帳號，優先評估 Google 登入，讓專案不必自行保管人員密碼。必須先解決 Apps Script 端的正式 token 驗證及帳號白名單，不能只加登入按鈕。如果 Dari 要求維持純 Apps Script、原帳密及不加外部驗證服務，則先以 PBKDF2-HMAC-SHA256 做實際 Apps Script 效能與正確性驗證；通過前不宣稱已解決 R7。

現況是加鹽 SHA-256 300 次；這是自製格式，不是 PBKDF2，也不是 bcrypt。加迭代次數、改函式名稱或只在前端雜湊，都不能直接當成完成改善。

## 比較

| 方案 | 在現有環境的作法 | 優點 | 代價與未確認事項 | 既有帳號遷移 |
| --- | --- | --- | --- | --- |
| **Google 登入** | 前端 Google Identity Services；後端可靠地驗證身分，再以專案自己的啟用狀態與角色授權 | 不儲存員工密碼；密碼重設與 Google 帳號驗證由 Google 負責 | 要有 OAuth 設定、允許的網站來源、可靠簽章驗證、網路與個別 Google 帳號；Google 登入不會自動給管理權。Apps Script 沒有現成 Node 驗證套件，須審核可靜態納入的驗證實作，或採外部受管驗證服務；後者的部署／費用待決 | 管理員事先核准各人的 Google `sub` 與原 admin_users id 關聯，保留 role、啟用狀態及歷史紀錄；不能只憑前端傳來 email 自動綁定。逐人驗證後停用本機密碼登入，失效舊 session；不要刪帳重建而失去核銷歸屬 |
| **PBKDF2-HMAC-SHA256** | 依標準實作 PBKDF2，使用 Apps Script 的 HMAC-SHA256 byte[] 介面，或經審閱的純 JS 實作靜態放入原始碼 | 無需外部驗證服務；保留帳密與角色流程；演算法及儲存格式可版本化 | 自行實作密碼元件仍需維護。高迭代數在 Apps Script 的耗時尚未實測，不能用本機 Node 成績代替。要測中文／Unicode、長密碼、salt、byte 符號轉換、標準向量及常數時間比對；限流也須保留 | 儲存版本、演算法、迭代數、salt 與導出值；舊格式先以原驗證器核對，只有正確登入當下用該次明文產生新格式，隨即丟棄明文。未登入者保留到 Dari 決定的截止日，屆時走受控重設流程 |
| **靜態納入純 JS bcrypt** | 不能 npm 安裝，但可在審核授權與來源後，把固定版本純 JS 實作納入程式 | 成熟生態；可版本化、逐步遷移 | 仍增加第三方程式維護；每個成本參數都要在 Apps Script 實測。bcrypt 有 72 bytes 限制，中文特別容易超過，不能默默截斷；目前系統已有長密碼時遷移更複雜 | 驗證舊格式後以新格式重建；不把舊雜湊當密碼再包一層。不符合長度規則者須受控重設 |
| **保留 SHA-256 300 次** | 現況 | 不需遷移 | 快速雜湊不足以作為建議的長期密碼方案；登入鎖定只能降低線上嘗試，不能防範雜湊外洩後的離線猜測 | 僅能作為遷移期舊驗證器，不能標成 R7 已修復 |

Apps Script 官方目前列出單次執行 6 分鐘、每使用者同時執行 30 次等限制；**6 分鐘是硬上限，不是合理登入等待目標**。上述方案均未做正式環境效能測試，也未承諾免費額度一定足夠。[Apps Script 配額](https://developers.google.com/apps-script/guides/services/quotas)

## PBKDF2 實作前的通過條件

- 採標準 PBKDF2 的 HMAC、區塊索引及 XOR 運算，不是反覆呼叫 SHA-256；用多組獨立標準向量與可信實作交叉驗證。建議每帳號獨立安全亂數 salt（至少 16 bytes）、32-byte 導出值，記錄參數以利將來升級。
- OWASP 現行 PBKDF2-HMAC-SHA256 建議迭代數為 600,000；不能為了通過時間測試就降回數百次並稱安全。若在 Apps Script 不可接受，應換驗證架構，而不是宣稱低成本自製 KDF 等價。bcrypt 僅列備選，成本至少 10 並實測。[OWASP 密碼儲存建議](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- 在 Apps Script 測新建／驗證／錯誤密碼的延遲、冷啟動、多位員工登入與限流；記錄 P50／P95、執行失敗及額度消耗。不得預先填入測試成績。
- 目前登入屬共用 ScriptLock 寫入流程，昂貴 KDF 若在這把鎖內運算，會連帶阻塞客人發券與核銷。Claude 應規劃短鎖的限流記帳與登入完成寫入，在重運算之外保護資料一致性；驗證完成後仍要重新檢查帳號啟用及角色，避免重現 R2。
- 調整或限制長密碼不得默默截斷；舊帳號、未登入帳號、重設流程、故障回復與截止日期均須可交接。新格式遷移不能由舊雜湊直接還原明文。

實作依據：[Apps Script Utilities 的 HMAC 介面](https://developers.google.com/apps-script/reference/utilities/utilities#computeHmacSha256Signature(Byte,Byte))、[RFC 8018 的 PBKDF2 定義](https://www.rfc-editor.org/rfc/rfc8018)。

## Google 登入不可省略的條件

Google 回傳身分證明後，後端須驗證簽章、發行者、目標 client id、期限，並處理適用流程的 CSRF／nonce 防護，再以 `sub` 關聯白名單帳號。僅解碼 JWT、相信瀏覽器 email，或允許任何 Google 帳號自動成為管理員都不可行。每次管理請求仍核對本系統角色及是否啟用。

Google 官方將 tokeninfo 端點定位為開發／除錯用途，不能把它當成本報告已認可的正式驗證方案。純 Apps Script 的驗證器如何維護金鑰輪替與快取，或是否另設受管驗證服務，是此方案的實作門檻。[Google ID token 後端驗證](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)

現有 Web App 以擁有者執行：`Session.getActiveUser().getEmail()` 可能為空；`getEffectiveUser()`／`ScriptApp.getIdentityToken()` 代表執行身分，不能直接拿來當每位現場員工身分。若改成以存取者執行，還會影響私有試算表的存取；不要為了登入就把整份資料表共用給所有 staff，也不要把客人入口改成必須 Google 登入。[Session 說明](https://developers.google.com/apps-script/reference/base/session)、[執行身分](https://developers.google.com/apps-script/guides/web)、[getIdentityToken 說明](https://developers.google.com/apps-script/reference/script/script-app#getIdentityToken())
