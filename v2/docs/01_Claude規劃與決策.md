## 三、架構（首選方案）

```
客人手機／工作人員
      │
      ▼
GitHub Pages：dari-design-web/survey-backend/v2/        ← 靜態頁面，免費
      │  POST text/plain JSON（不觸發跨網域預檢）
      ▼
Google Apps Script 網頁應用程式（綁定在試算表）          ← 執行身分為擁有者，免費額度
      │
      ▼
Google 試算表（每個資料集合一個分頁）
```

- **GitHub** 是程式的唯一正式版本。`v2/gas/VERSION` 只有在測試通過後才會改。
- **Apps Script 每小時檢查 GitHub**：若 VERSION 有新版，就把程式更新到同一個部署網址，網址不變。後台「帳號」頁也有手動更新按鈕。
- **舊版不受影響**：`survey-backend` 根目錄的舊頁面與 Replit 後端都沒有動。新版放在 `v2/` 子資料夾，確認可用後才切換入口與 QR Code。

選擇理由：
- 原本前端所有 API 呼叫都經過 `js/api.js`，只要換掉傳輸層，其餘 15 個頁面幾乎不用改。
- Apps Script 只有一個專案、一把 `ScriptLock`，所有寫入（發券、核銷、庫存）都經過同一個入口協調，符合 00 號文件第六節的要求。

### 何時該改用其他服務（替代方案的觸發條件）

| 條件 | 建議 |

## 五、贈品庫存規則

1. **不儲存可被改壞的計數**。
   - 實際庫存 = 所有庫存異動紀錄（`stock_logs.on_hand_delta`）的加總。
   - 已預留 = 該贈品「狀態為已發出、尚未過期」的券數。
   - 可發 = 實際庫存 − 已預留。
   - `gifts` 分頁上的三個數字只是顯示用的快照。
2. **發券**：在鎖內確認可發 ≥ 1 才發券。不會超發，也不會出現負庫存。
3. **核銷**：券狀態改為已兌換，並寫入一筆「核銷出庫 −1」。結果是實際庫存 −1、已預留 −1，可發數量不變。
4. **逾期或作廢**：預留自動消失，因為已預留是即時計算的，不需要「釋放」動作，也就不會重複釋放。
5. **手動異動**：分入庫、耗損、盤點三種。
   - 耗損與盤點必須填寫原因。
   - 調整後的實際庫存不可少於已預留，避免已承諾的贈品消失。
   - 只有 super／admin 可以操作，每筆都留紀錄。
6. **中途失敗恢復**：每天凌晨 3 點自動執行對帳，super 也可在後台手動執行。
   - 已核銷但缺少出庫紀錄的券，以券編號為鍵補登一筆，重跑不會重複。
   - 把逾期券標記為 expired，並重算快照。
7. **問卷沒有指定贈品時**：與原版相同，不限量發券。
